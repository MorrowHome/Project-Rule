## 0. 一句话结论

快照的采集 / 恢复 / 环形缓冲已经跑通。接手要解决的是两件事：

1. **快照名册错了**：采集的是「当前启用中的实体」，采集时禁用的对象不在快照里 → 「世界回到那一刻」对它们不成立。（G1）
2. **规则效果在恢复后不重施**：快照恢复按契约不触发任何规则事件，而质量 / 摩擦靠实体订阅 `OnRulesChanged` 才施加、重力直接写 `Physics2D.gravity` 且**根本不在快照里** → 回溯后「规则表回去了，物理效果没回去」。（G2，本次新发现）

一句话：**位置速度回得去，规则造成的物理效果回不去。**

## 2. 核心矛盾与缺口

### G1 名册只含「启用中」的对象 ✅ 已确认改法

`SnapshotSystem.Capture` 遍历 `_registry.All`，而 `WorldRegistry` 的契约是 **`OnEnable` 登记 / `OnDisable` 注销**；
`ObjectStates` 又在同一个循环里逐实体追加，与 `Entities` 严格 1:1。

> t=1 门被禁用 → 拍 S1（门不在 S1 里）→ t=2 门被重新启用 → 恢复 S1 → **门还开着**。

**已定**：快照名册的**成员资格 = 生命周期**（扫描登记 / `OnDestroy` 注销），与启用状态解耦。

### G2 规则效果的「施加」没有中央触发点 ⚠️ 本次修正

v1 说「注册表今天只在服务快照」是**错的**：`DamageProcessor` 构造就吃 `IWorldRegistry`，
因果扩散的候选集就是 `_registry.All`（`DamageProcessor.cs:33 / 247-249`）。规则侧依赖注册表**本来就有**。

真正的问题是另外两条：

**G2-a 恢复后没有任何东西重施规则效果。**
快照恢复的契约是「不触发任何规则事件」（`接口与事件定义.md` §2.5 表：`RestoreSlots` 对
`Clear` / `OnRuleExpired` / `OnRulesChanged` **全是 ✗**），需要收尾的模块自己订阅 `OnRestored`——
而现在 `OnRestored` 零订阅者。后果：

| 恢复后 | 现状 |
| --- | --- |
| 质量 / 摩擦 | `AttributeValues` 被写回，但**没有实体重新读** → 刚体质量与材质还是回溯前的 |
| 重力 | `Physics2D.gravity` **不在快照里**（`AttributeValues` 明确排除重力），`GravityRule` 也不轮询 → 回溯跨过重力规则后重力是错的 |
| 时间 | `TimeRule` 每帧对表侥幸对上 —— 这是同一个问题的局部补丁 |
| 伤害 / 因果 | `DamageProcessor` 每次结算现读 `AttributeValues` → 这条**没问题** |

也就是说：「世界回到那一刻」目前只对**位置 / 速度 / 实体状态**成立，对**规则造成的物理效果**不成立。

**G2-b 施加的触发点是分散的。** 实体各订阅 `OnRulesChanged`、重力规则不订阅、时间规则轮询——
三种模式并存，恢复这条路径就没人接。需要一个统一的「效果已变化 / 需重施」信号。

> **关于「规则统一修改 vs 实体自读」**：两条都成立，但这次暴露的 bug **不是方向选错**，是触发点缺失。
> - 自读的收益：新生成的实体在 `OnEnable` 登记后立刻拿到最新值，**不需要注册表发登记事件**。
> - 自读的代价：施加时机由实体自己掌握，恢复路径容易漏（就是现在）。
> - 若改成「规则遍历注册表写物理」：机制代码（摩擦的独占材质克隆）仍在 `RuleAffectedBody`，
>   规则只多一次遍历；但**必须补一个「实体登记 → 立刻施加当前规则」的钩子**，否则新实体漏规则。
> **建议**：保留自读（值在 `IAttributeManager`，机制在 `RuleAffectedBody`），
> 但把「何时施加」收成**中央信号**，并保证恢复后一定发一次。详见 §3.4。

### G3 存储散在规则类 ⚠️ 按讨论修订

- **何时拍**（缓冲间隔、定点时机）→ **留在规则类**，这是规则策略。
- **拍下来存哪**（环形缓冲 + 定点快照）→ **统一归快照系统**，规则类不再持有 `Snapshot`。

现状违反后半条：`TimeRule` 自己持有 `_fixedPoint`，而 `_buffer` 在 `SnapshotSystem`。

### G4 定点快照不在快照里（隐式第二真相）

`Snapshot` 不装 `_fixedPoint`，所以恢复一张「恒定生效中」的表后，
`TimeRule` 只能每帧对表补拍。按 G3 的修订，定点**存储**进快照系统（`Pin/Unpin` 句柄），
「何时 Pin」仍由规则类决定，补拍逻辑退化为恢复后的对齐。

### G5 `ISnapshotParticipant` 的 null 语义与类型安全

恢复侧用 `es.ModuleState != null` 判空：参与者合法返回 `null` 会被静默跳过；
`object` 无类型约束，恢复靠强转。建议：禁止返回 `null`（用空结构体/哨兵），恢复时校验类型并告警。

### G6 运行时新生成对象缺少统一约定

恢复时只处理「当前存在、不在快照里、实现了 `ISnapshotParticipant` 且 `DiscardWhenMissing`」的对象。
新增弹体/召唤物若忘实现接口，回溯后会留在世界里。要写进规范并有测试兜底。

### G7 重开关卡语义 ✅ 已定（选项 1）

| 出处 | 说法 |
| --- | --- |
| 架构 §3.2 | 「关卡开始时拍一张，重开 = 恢复它」 |
| 架构 §6.1 | 「重开 = 加载关卡场景（世界回到设计初态）→ 读存档的规则 → 重新应用」 |

**已定：走 §6.1（场景重载 + 存档重放）。** 后果：
- 快照的消费者从三个减到**两个**（时间恒定 / 时间反转）；
- 架构 §3.2 里「关卡流程（重开关卡）用快照」这句要删；
- 「关卡开始时拍一张」这个需求**取消**，快照不必覆盖「采集后被销毁的对象」。

### G8 冻结文档未同步

`Snapshot.Seq`、`RestoreMode`、`EntityState.ModuleState` 都不在 `接口与事件定义.md` §3.2。

### G9 采集的 GC 与成本（后置）

每次 `Capture()` 新建 `Snapshot` + 两个 `List` + N 个 struct，每 5 秒一次。

### G10 直接写刚体的穿越风险（标注）

恢复直接 `body.position =` / `body.linearVelocity =`。玩家是 Kinematic（D1）没问题；
Dynamic 物体是瞬移，薄碰撞体有穿越风险。加一条回归用例。

## 3. 目标架构

### 3.1 职责划分

| 职责 | 承担者 | 回答的问题 |
| --- | --- | --- |
| **名册 Roster** | `ISnapshotRoster` + `SnapshotScope` | 谁进快照？（**生命周期**） |
| **引擎 Engine** | `ISnapshotSystem` / `SnapshotSystem` | 采什么、怎么还、**存哪**？ |
| **策略 Policy** | `TimeRule` / 关卡流程 | **何时**拍、拍哪一张？ |
| **施加 Apply** | `RuleAffectedBody`（机制）+ 中央信号（时机） | 规则效果何时落到世界？ |

铁律不变：下层不认识上层。快照系统只认 `IRuleAffected` / `ISnapshotParticipant` / `IRuleSystem`。

### 3.2 两个集合，两种成员资格（G1 + G2）

同一个实体，两张表，各自服务不同的消费者：

| 集合 | 成员资格 | 消费者 | 现在的问题 |
| --- | --- | --- | --- |
| `IWorldRegistry`（活动实体） | `OnEnable` 进 / `OnDisable` 出 | 伤害扩散（`DamageProcessor`）、规则施加目标集 | 语义正确，**保持不变** |
| `ISnapshotRoster`（快照名册） | **扫描登记 / `OnDestroy` 出** | `SnapshotSystem` | 新增；解决 G1 |

> **为什么必须扫描**：Unity 对**初始就禁用**的对象不会调 `Awake` / `OnEnable`，
> 所以「禁用中的预置对象」不会自己登记——这正是 G1 的根因。

```csharp
// Infrastructure/Shared/Snapshot/ISnapshotRoster.cs
public interface ISnapshotRoster
{
    void Register(IRuleAffected target);     // 扫描登记 + 运行时生成
    void Unregister(IRuleAffected target);   // 仅 Destroy / 场景卸载
    IReadOnlyList<IRuleAffected> Targets { get; }
}
```

`SnapshotScope`（MonoBehaviour，挂在关卡根 `LevelRuntime`）：

```csharp
public sealed class SnapshotScope : MonoBehaviour
{
    [SerializeField] private Transform _root;   // 留空 = 自身
    private void Awake() => SnapshotRoster.Instance?.Rebuild(_root != null ? _root : transform);
}
```

`Rebuild` = `root.GetComponentsInChildren<IRuleAffected>(includeInactive: true)`。

**代价（要认）**：每个快照对象要维护两条登记。集中在 `RuleAffectedBody` 与生成器两处，
并加一条验证断言「两表成员一致」，防止漂移。

> 备选（D6）：**一个注册表两个视图**（`Active` / `All`，成员资格=生命周期，用 flag 标记启用）。
> 好处是只登记一次；代价是 `IWorldRegistry` 语义变更，且 `DamageProcessor` 必须从 `All` 改用 `Active`
> （否则扩散会打到禁用对象）。**建议先走两个集合，风险小。**

### 3.3 采集与恢复

```
Capture（遍历 roster.Targets，含禁用）:
  EntityState { Body, Position, Velocity, Rotation, AnimatorHash/Time, Status, ActiveSelf, ModuleState }
  rules.Table.SnapshotSlots() + rules.Attributes.Values

Restore(snap, mode):
  ① 名册里有、快照里没有、且 DiscardWhenMissing → SetActive(false)   （回退后未来作废）
  ② 逐条写回 ActiveSelf（含「当时就是禁用」的对象）
  ③ 写回规则表（含 Remaining）+ 属性管理器
  ④ 逐实体写回 物理量 → 动画 → EntityStatus（KeepEnergy 用 Clone 保留当前能量）→ ModuleState
  ⑤ 重建规则效果 ← 新增，见 3.4（重力 / 质量 / 摩擦必须在这里重施）
  ⑥ OnRestored 广播
```

**建议（D4）**：`ObjectActiveState` 并入 `EntityState.ActiveSelf`。名册统一后两者天然 1:1。

### 3.4 规则效果的中央触发（G2 的解法）

保留自读，但把「何时施加」收成一个中央信号：

```
OnRulesChanged（规则变更）  ─┐
                            ├─▶ IRuleSystem.OnEffectsChanged ──▶ RuleAffectedBody.Apply()
OnRestored（快照恢复）      ─┘                                  GravityRule 重写 Physics2D.gravity
```

具体（建议 D5）：

1. `IRuleSystem` 新增**静默重施**入口 `ReapplyActiveEffects()`：
   遍历 6 个规则类，按**当前槽位**重新施加，**不调 `Request`、不发 `OnRuleActivated` / `OnRuleExpired`**
   （与 §2.5 契约一致）。
2. `SnapshotSystem.Restore` 在第 ③ 步之后、`OnRestored` 之前调用它 →
   保证「表已回去、效果也回去了」再广播，顺序确定。
3. `GravityRule.Reapply` 重写 `Physics2D.gravity`；`TimeRule` 的对表逻辑复用；
   质量 / 摩擦由 `AttributeValues` 重写后触发一次实体重读。
4. 实体侧：`RuleAffectedBody` 订阅 `OnEffectsChanged`（或沿用 `OnRulesChanged` + 新增恢复后广播），
   不再依赖「谁记得发事件」。

> 这一条动到冻结的 `IRuleSystem`，需要并进 `接口与事件定义.md`。
> 替代方案（改动更小但更容易漏）：各模块自己订阅 `OnRestored`。

### 3.5 存储归位（G3 + G4）

**规则类决定何时拍，快照系统统一存：**

```csharp
public interface ISnapshotSystem
{
    Snapshot Capture();
    void     Restore(Snapshot snap, RestoreMode mode = RestoreMode.Full);

    // 环形缓冲（反转）—— 规则类决定节奏，系统负责存
    int  CaptureToBuffer();
    bool TryPeekSecondLast(out Snapshot snap);
    void DiscardNewerThan(int index);
    void ClearBuffer();

    // 定点（恒定）—— 新增：规则类决定何时 Pin，存储归系统
    int  Pin();
    bool TryRestorePinned(int handle, RestoreMode mode);
    void Unpin(int handle);

    event Action OnRestored;
}
```

- `TimeRule.RollSnapshotBuffer` **保留**（节奏是规则策略），仍调 `CaptureToBuffer()`；
  **不新增** `SnapshotSystem.Tick`。
- `TimeRule._fixedPoint` **删除**，改用 `Pin()` / `TryRestorePinned()` / `Unpin()`；
  定点槽不参与快照内容，一次缓冲回溯不会把它冲掉。

### 3.6 扩展点契约

1. `CaptureSnapshotState()` **禁止返回 `null`**；无状态返回空结构体/哨兵。恢复侧校验类型，失败告警跳过。
2. `DiscardWhenMissing` 只对**运行时生成**对象为 `true`。
3. 任何「生成后影响世界、回溯后不该留下」的对象，**必须**实现 `ISnapshotParticipant` 且在名册里。
4. `OnRestored` 订阅者只做**收尾**（重启特效、对齐外部状态），不在恢复过程中回写世界。
5. 粒子 / 拖尾不进快照，恢复时由订阅者重启——这是设计。

### 3.7 与存档的边界（不变）

| | 快照 Snapshot | 存档 SaveData |
| --- | --- | --- |
| 生命周期 | 运行时内存 | 磁盘，跨关卡 |
| 内容 | 位置/速度/动画/实体状态/规则槽/属性值 | 已解锁词条、跨关卡激活规则、激活历史、进度、玩家状态 |
| 铁律 | 绝不序列化 Transform / Rigidbody（C5） | 同左 |
| 交集 | 仅 `EntityStatusData` | 同左 |

## 5. 决策

### 已定（本次讨论）

| # | 决策 | 结论 |
| --- | --- | --- |
| **D1 / G1** | 快照名册成员资格 | **= 生命周期**（扫描登记 / `OnDestroy` 注销），与启用状态解耦 |
| **D2 / G7** | 重开关卡语义 | **场景重载 + 存档重放规则**；快照只服务恒定 / 反转 |
| **D3 / G3** | 拍照的职责边界 | **何时拍归规则类，存哪归快照系统**（定点也进系统，用 Pin 句柄） |

### 待定

| # | 决策 | 选项 | 建议 |
| --- | --- | --- | --- |
| **D4** | `ObjectActiveState` | ① 并入 `EntityState`；② 保持独立 List | **①** |
