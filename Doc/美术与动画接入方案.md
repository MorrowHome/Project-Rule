## 二、导入设置（已定）

| 项 | 值 | 理由 |
| --- | --- | --- |
| Texture Type | **Sprite (2D and UI)** | — |
| Sprite Mode | **Single** | 每帧一个文件，不做图集切片 |
| **Pixels Per Unit** | **640** | 见下 |
| Filter Mode | **Bilinear** | ⚠️ **这是手绘线条画，不是像素画**——Point 会让线条出锯齿 |
| Generate Mip Maps | **关** | 2D |
| Alpha Is Transparency | **开** | — |
| Pivot | **Custom**（见 §三）| 每个序列不同 |

### PPU = 640 是怎么来的

- 摄像机 `orthographic size = 4` → 屏幕高 **8 世界单位**
- 玩家胶囊碰撞箱 **1×1 单位**（白盒精灵也是 1 单位）
- 角色站立帧实测 **699 px 高** → `699 / 640 = 1.09 单位`
  → 比碰撞箱高 9%（头发略出头），**碰撞箱、摄像机、关卡尺寸全都不用动** ✓

### 🔴 未解决：纹理内存

裁切后仍有 **≈1.3 亿像素**、212 张贴图：

| 方案 | 显存占用 |
| --- | --- |
| 当前分辨率（PPU 640）| 未压缩 ≈ **520 MB** / DXT5 ≈ 130 MB ✗✗ |
| **整体缩小 4 倍 → PPU 160** | 未压缩 ≈ 32 MB / DXT5 ≈ 8 MB ✓✓ |

**世界里的尺寸完全不变**（缩小 4 倍 + PPU 除以 4 = 同样的世界大小），
而 1080p 下角色约显示 147 px，贴图留 175 px → 1.2 倍超采样，够用 ✓

> **建议顺序**：先把美术提交进 git → 再跑一次 `/4 + PPU 160`，随时可回退。

## 三、轴心（已定）

### 规则：**脚底中点** —— `pivot = (质心x, 裁切框底边)`

- **x 用 alpha 质心**，不用包围盒中点。围巾是飘起来的、剑是伸出去的，
  它们会把包围盒拽偏，但**质量集中在身体上**，质心稳。
- **y 用底边**（脚）。
- 裁切：每个序列裁到「**该序列所有帧的并集包围盒**」——
  ⚠️ **不是按帧裁**。序列内部的帧间位移是**故意的**（挥剑前冲、翻滚），按帧裁会把动作裁没。

### ⚠️ 为什么不给空中姿势特判

翻滚姿势（`Airborne` / `Land` / `WallJump` / `Weightless`）是卷身动作，
脚是收起来的，所以「底边 = 脚」并不严格成立。

但**空中没有地面线可以比对** —— 那里差几十像素谁也看不出来；
而**落地姿势的脚必须踩在地面线上**，那才是必须对的地方。
所以统一用一条规则，不为空中姿势搞特例 ✓

## 四、谁驱动动画（已定）

**`PlayerController` 不认识 Animator。** 新增 **`PlayerAnimationDriver`**，
放在 **`Scripts/Presentation/Player/`**
（`RuleGame.Presentation` 的 asmdef 已依赖 `RuleGame.Gameplay` ✓ 架构上也对：表现层依赖玩法层）。

```
PlayerController ──读只读状态──► PlayerAnimationDriver ──CrossFade──► Animator
```

### 要给 `PlayerController` 补的只读属性（只加，不改行为）

```csharp
/// <summary>当前速度（自己维护的那个，不含击退）。动画用。</summary>
public Vector2 Velocity => _velocity;

/// <summary>当前朝向：+1 右 / -1 左。</summary>
public float Facing => _facing;
```

### 边沿事件由 driver 自己推导，**不要给 `PlayerController` 加事件**

| 事件 | 怎么推 |
| --- | --- |
| 落地 | `IsGrounded` false → true |
| 起跳 / 蹬墙 | `JumpsLeft` 变大（蹬墙会刷新到满）|
| 蹬墙跳 | 同一帧里 `JumpsLeft` 变大 **且** (`WallLeft` 或 `WallRight`) |
| 起冲 | `IsDashing` false → true |

好处：`PlayerController` 保持干净；driver 是纯「读状态 + 推状态」，换成敌人控制器也能复用。

## 五、状态机路线：**代码选状态**（已定，附说明）

### 这仍然是状态机，区别只在「过渡条件写在哪」

| | 过渡条件写在 | 怎么切 |
| --- | --- | --- |
| 传统做法 | **Animator 窗口**（连线 + Parameter）| 引擎每帧求值，自动切 |
| **本项目** | **C# 代码** | driver 算出当前状态，`CrossFadeInFixedTime` 过去 |

Animator 里**每个动画一个 state，彼此不连 Transition**。

### 诚实说明：传统做法才是「最通用」的

- **Animator 窗口连线是 Unity 的默认/教程做法**，多数项目这么干 ✓
- 代码驱动**也很常见**（动作游戏尤其多），但它是「一种流派」而非「标准答案」✓
- ⚠️ **更正一个之前的夸大说法**：我曾说「自动过渡会导致快照回滚后动画不对」。
  其实没那么严重 —— 恢复后 driver 会用恢复过的物理状态重新算参数，条件会收敛到正确状态，
  顶多多一帧抖动。**回滚不是决定性理由。**

### 真正的理由是这两条

1. **状态多 + 相互打断**。22 个序列，且几乎每个动作都能打断别的（空中冲刺、滑墙中跳、
   受击打断一切）。在 Animator 窗口里画这几十条条件线会变成蜘蛛网，改一个条件要顺着连线找半天。
2. **代码能 review**。条件写在 C# 里，队友能在 diff 里看清「什么情况播什么」，能 `git blame`。
   Animator 的图在 git 里是二进制，**没法 diff、没法 review**。

> 想换回传统路线随时可以：driver 的代码形状几乎不变（它本来就算出了当前状态，
> 只是把 `CrossFade(hash)` 换成 `SetBool/SetTrigger`）。

## 六、⚠️ driver 的状态优先级必须和 `FixedUpdate` 的分支顺序一致

**`PlayerController` 不是状态机**，它是**扁平的优先级级联** —— 每个物理帧按固定顺序求值
（① 接地 → ② 跳数 → ③ 冲刺 → ④ 重力 → ⑤ 水平 → ⑥ 贴地 → ⑦ 跳跃 → ⑧ 削速 → ⑨ 击退 → ⑩ Slide），
没有 `enum State`、没有转移表。**这是故意的**：平台动作游戏里「一切能打断一切」，
写经典 FSM 会状态爆炸；扁平级联让动作能自由组合。

**后果**：玩法没有状态，**动画的状态得由 driver 从这些标志推出来**，
而且推的**优先级必须对齐 `FixedUpdate`**，否则会出现「物理在冲刺、动画在走路」：

| driver 判定顺序 | 对应 `FixedUpdate` 的哪一步 |
| --- | --- |
| 1. `IsDashing` → `Dash` | ⑤ 冲刺接管水平 |
| 2. `IsWallSliding` → `WallSlide` | ④′ 贴墙下滑 |
| 3. 落地边沿 → `Land` | — |
| 4. 空中 → `JumpStart` / `Airborne`（按沿 `_up` 的速度正负）| ④ 重力 |
| 5. `|vx| > ε` → `Walk` / `Run` | ⑤ 水平 |
| 6. 否则 → `Idle` | — |

> ⚠️ 判「上升/下降」要用**沿 `_up` 的分量**，不是世界 y —— 重力反转后二者相反。

## 七、朝向与翻转（已定）

### 朝向：**直接用 `PlayerController.Facing`，不需要额外检测**

`_facing` 在接地分支里取的是**换算后**的方向，所以「摩擦 × 反转」时你按右往左走，
`Facing` 自动是 −1、精灵自动朝左 ✓ **方向检测这件事已经做完了** ✓

### 翻转：**`spriteRenderer.flipX = Facing < 0`**

不翻 `Visual` 子物体的 scale，也不翻根物体：

| 做法 | 评价 |
| --- | --- |
| **`flipX`** | ✅ 一行；绕精灵自己的轴心镜像，精确；不碰 transform |
| 翻 `Visual` 子物体 scale | 整棵子树跟着翻（挂武器/特效点自动镜像）—— 但**目前没有需要翻的子物体** |
| 翻**根物体** scale | ❌ 会连碰撞箱一起翻；Rigidbody2D 上挂负缩放 Unity 会警告 |

因为**剑是画在帧里的**（拔剑/挥剑/收剑整套都是角色帧，没有单独的武器物体）✓ 所以 `flipX` 够用。

> 📌 以后若加了「特效挂点」这类子物体，`flipX` 不会翻它 —— 那时再换 `Visual` 方案。

## 八、重力反转 / 暂停（已定）

### 重力反转：**用专门的动画，不做 `flipY`**

`Weightless`（失重倒转，14 帧）就是为这个准备的 ✓
driver 读到重力被反转（`Physics2D.gravity` 与默认反向）时播它，**不翻精灵**。
（这比「先不颠倒」更好 —— 美术已经给了正向的表达。）

### 暂停：`animator.speed = 0`

架构 §3.1 说「动画用 `Normal` 模式跟随 `Time.timeScale`，无需手动分发」，
但 **D18 决定暂停时 `Time.timeScale` 保持 1**（用 `Physics2D.simulationMode = Script` 停物理）。
**两者一起看：暂停时动画会继续播** ✗ 拼装界面一开，角色还在原地跑跑步机。

**方案**：driver 订阅 `EntityStatus.IsPaused`，暂停时 `animator.speed = 0`、恢复设回 1 ✓

> ⚠️ **敌人的 Animator 也要同样处理** —— 这条要同步给 P1（时间管理器）和 P4。

## 十、攻击（下一步）：**命中窗口由代码拥有**

攻击有 起手 / 生效 / 收招 三段，命中判定只在「生效」段开窗。

| 做法 | 评价 |
| --- | --- |
| Animation Event 在剪辑时间轴上开/关判定 | ❌ 事件挂在**剪辑时间轴**上——快照恢复、变速、动画被中断时都难保确定性；美术剪掉一帧就可能悄悄打乱判定 |
| **代码拥有窗口**（建议）：`_attackWindup` / `_attackActive` / `_attackRecover` 三个序列化秒数，`FixedUpdate` 里按计时开窗 | ✅ 完全可预测、可快照、可单测；动画**只负责看起来对** |

判定窗口与动画时间轴**解耦**，美术调节奏不用改数值 ✓

## 十二、Python 工具（做过的两件事，可复用）

**裁切 + 算轴心**（每个序列取并集包围盒，所有帧裁到同一矩形）：

```python
from PIL import Image
import os, glob
L=T=10**9; R=B=-1; sx=sw=0.0
ims=[(f, Image.open(f).convert('RGBA')) for f in sorted(glob.glob('Idle/*.png'))]
for f,im in ims:
    bb = im.getchannel('A').getbbox()
    L=min(L,bb[0]); T=min(T,bb[1]); R=max(R,bb[2]); B=max(B,bb[3])
for f,im in ims:                       # alpha 质心 → 轴心 x
    a = im.getchannel('A')
    for y in range(im.size[1]):
        for x,v in enumerate(a.crop((0,y,im.size[0],y+1)).getdata()):
            if v: sx += x*v; sw += v
box=(L,T,R,B)
for f,im in ims: im.crop(box).save(f)  # 同一矩形，保住帧间位移
nx = (sx/sw - L) / (R-L)               # → spritePivot.x，y 恒为 0
```
