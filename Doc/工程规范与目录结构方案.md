## 一、Unity 到底有没有官方编码规范

### 1.1 C# 代码：**有**

| 官方资源 | 地址 |
|---|---|
| 官方电子书《Use a C# style guide for clean and scalable game code (Unity 6 版)》 | `unity.com/resources/c-sharp-style-guide-unity-6` |
| 官方示例仓库 `Unity-Code-Style-Guide` | `github.com/thomasjacobsen-unity/Unity-Code-Style-Guide` |
| 官方文章：命名与代码风格技巧 | `unity.com/how-to/naming-and-code-style-tips-c-scripting-unity` |
| 官方文章：格式最佳实践 | `unity.com/how-to/formatting-best-practices-c-scripting-unity` |

官方原文（抓自 unity.com）：

> "The recommendations shared here are based on those provided by **Microsoft**. The best code style guide rules are the ones that work best for your team's needs."
>
> "The guidelines we provide are **recommendations, not hard and fast rules**. … The specifics of an individual rule are less important than having everyone agree to follow it consistently."

**三点结论**：

1. Unity 的规范是 **Microsoft Framework Design Guidelines 的子集**，不是自创体系
2. 官方明确说这是**推荐而非强制**，且**团队自己的指南优先**
3. 官方给了可下载的电子书 + 示例仓库，**直接拿来改比从零写快得多**

### 1.2 资源命名：**没有** UE 那样的前缀体系

UE 有 `BP_`（蓝图）/ `SM_`（静态网格）/ `M_`（材质）/ `T_`（贴图）这类**强制双字母前缀**。
**Unity 没有，官方也没打算有。**

原因是机制不同：

| | Unreal Engine | Unity |
|---|---|---|
| 资源引用方式 | 路径 + 名称 | **`.meta` 文件里的 GUID** |
| 改名的影响 | 可能断引用（要靠重定向器） | **不断引用**（GUID 不变） |
| 前缀体系的作用 | 技术必需 | 纯人类可读性 |

**所以 Unity 的资源命名约定是「团队自定」的**，官方不提供，因为技术上不需要。

但它仍然值得定——4 个人在 Project 窗口里找东西，需要可预测性。

## 二、目录结构方案

### 2.1 设计原则

| 原则 | 说明 |
|---|---|
| **按架构分层，不按文件类型** | 目录结构直接映射 [系统模块架构.md](系统模块架构.md) 的四层 |
| **`_Project/` 包裹** | 下划线让团队内容排在 Project 窗口最前，与导入的包分开 |
| **一个程序集一个目录** | Assembly Definition 的作用域与目录一一对应 |
| **路径无空格、无中文** | 避免命令行 / CI 出问题 |

### 2.2 完整结构

```
Assets/
├── _Project/
│   ├── Scripts/
│   │   ├── Infrastructure/           ← 基础设施层（零依赖）
│   │   │   ├── Time/                 时间管理器
│   │   │   ├── Snapshot/             快照系统
│   │   │   ├── LevelFlow/            关卡流程
│   │   │   └── Common/               对象注册表、通用工具
│   │   ├── Rules/                    ← 核心层
│   │   │   ├── Table/                规则维护表
│   │   │   ├── Attributes/           属性管理器
│   │   │   ├── AttributeRules/       7 个属性规则类（一人一个）
│   │   │   └── Data/                 RuleDef 等数据定义
│   │   ├── Gameplay/                 ← 玩法层
│   │   │   ├── Player/
│   │   │   ├── Enemy/
│   │   │   ├── Combat/
│   │   │   └── Scene/                场景触发器、NPC 台词
│   │   ├── Persistence/              存档
│   │   ├── UI/                       HUD、拼装界面、结算
│   │   ├── Presentation/             摄像机、VFX、音频
│   │   └── Editor/                   编辑器脚本（仅编辑器编译）
│   ├── Art/
│   │   ├── Sprites/
│   │   ├── Animations/
│   │   └── Materials/
│   ├── Audio/
│   │   ├── SFX/
│   │   └── Music/
│   ├── Data/                         ScriptableObject 资产实例
│   │   ├── Rules/                    每个规则一个 .asset
│   │   └── Config/
│   ├── Prefabs/
│   ├── Scenes/
│   └── Settings/                     URP 设置（从模板挪进来）
├── Plugins/                          第三方二进制
└── (模板原有的 Scenes/ Settings/ 合并进 _Project/)
```

### 2.3 与架构层的对应

| 目录 | 架构层 | 允许依赖 |
|---|---|---|
| `Infrastructure/` | 基础设施 | **无** |
| `Rules/` | 核心 | Infrastructure |
| `Gameplay/` | 玩法 | Rules, Infrastructure |
| `Persistence/` | 支撑 | Rules, Infrastructure |
| `UI/` · `Presentation/` | 支撑 / 表现 | 全部 |
| `Editor/` | 工具 | 全部（仅编辑器） |

> 这张表就是 [系统模块架构.md](系统模块架构.md) 里那三条「铁律」的目录版。

## 三、Assembly Definition 方案

**4 个人必须用 asmdef，这不是可选项。** 三个理由：

| 理由 | 说明 |
|---|---|
| **强制分层** | 架构里写的「规则系统不认识玩家/敌人」从**代码评审意见**变成**编译错误** |
| **编译快** | 改一个文件只重编一个程序集，不是整个工程 |
| **防循环依赖** | 循环引用直接编译不过，逼你在设计阶段解决 |

### 建议的程序集划分

| 程序集 | 依赖 | 目录 |
|---|---|---|
| `RuleGame.Infrastructure` | — | `Scripts/Infrastructure/` |
| `RuleGame.Core` | Infrastructure | `Scripts/Rules/` |
| `RuleGame.Gameplay` | Core, Infrastructure | `Scripts/Gameplay/` |
| `RuleGame.Persistence` | Core, Infrastructure | `Scripts/Persistence/` |
| `RuleGame.UI` | 全部 | `Scripts/UI/` |
| `RuleGame.Presentation` | 全部 | `Scripts/Presentation/` |
| `RuleGame.Editor` | 全部 | `Scripts/Editor/`（`includePlatforms: [Editor]`） |

> ⚠️ **`Persistence` 必须独立于 `Core`**。存档要订阅 `OnRuleActivated`（依赖 Core），
> 如果塞进 Core 就成了循环依赖。

> 📌 **为什么是 7 个而不是 6 个**：asmdef 只覆盖自己所在目录及其子目录，**管不到兄弟目录**。
> 所以 `Scripts/UI/` 和 `Scripts/Presentation/` 不可能共用一个 asmdef，只能各建一个。

**如果嫌 7 个太多**，可以退到 3 个：`RuleGame.Core`（Infra+Rules+Persistence）/ `RuleGame.Gameplay` / `RuleGame.UI`。
但那样就失去了强制分层的能力，架构会慢慢烂掉。**建议就用 7 个**——一次性成本很低。

> ✅ **已于本次执行完毕**：7 个 asmdef 已创建，依赖关系见上表。

## 四、命名规范

### 4.1 C# 代码（基于 Unity 官方指南）

| 对象 | 规范 | 示例 |
|---|---|---|
| 类 / 结构 / 枚举 | PascalCase | `RuleTable`, `AttributeId` |
| 接口 | `I` + PascalCase | `IRuleSystem` |
| 方法 | PascalCase，**动词开头** | `Request`, `TryConsumeEnergy` |
| public 字段 / 属性 | PascalCase | `TimeScale` |
| 私有字段 | `_` + camelCase | `_ruleTable` |
| 局部变量 / 参数 | camelCase | `deltaTime` |
| 常量 | PascalCase | `MaxSnapshotCount` |
| 事件 | PascalCase，`On` 开头 | `OnRuleActivated` |
| 事件处理方法 | `On` + 事件名 | `OnRuleActivatedHandler` |
| 命名空间 | `RuleGame.<层>.<模块>` | `RuleGame.Core.Rules` |

**官方明确的一条**：**不要在标识符里用特殊字符**（反斜杠、符号、Unicode 字符），
即使 C# 允许——它们会干扰 Unity 的命令行工具。**所以类名和文件名都用 ASCII**。

**其他约定**：

| 项 | 约定 |
|---|---|
| 缩进 | 4 空格，**不用 Tab** |
| 大括号 | 另起一行（Allman） |
| 一个文件一个类型 | 文件名 = 类型名 |
| `var` | 类型明显时可用，否则写全 |
| 可空 | 开启 `<Nullable>enable</Nullable>`（可选） |

### 4.2 资源命名（我们自定，Unity 没有官方体系）

**核心选择：用后缀，不用前缀。**

原因：Unity 的 Project 窗口**按名称排序**。UE 用前缀（`SM_Chair`、`T_Chair`）是为了让同类资源排在一起；
但前缀会让「同一个对象的所有资源」分散开（`Chair` 的网格、贴图、材质分别在三个地方）。

我们用后缀，让同一个对象的所有资源**排在一起**：

| 资源类型 | 规范 | 示例 |
|---|---|---|
| 场景 | `Level_` + 两位序号 | `Level_01.unity` |
| 预制体 | PascalCase | `Player.prefab`, `Stone.prefab` |
| 精灵（帧序列） | `名字_动作_两位序号` | `Hero_Run_01.png` |
| 精灵（单张） | `名字_用途` | `Hero_Idle.png`, `UI_Icon_Gravity.png` |
| 动画剪辑 | `名字_动作` | `Hero_Run.anim` |
| 动画控制器 | 名字 | `Hero.controller` |
| 材质 | `名字_Mat` | `Outline_Mat.mat` |
| ScriptableObject | `用途_Rule` | `GravityRevert_Rule.asset` |
| 音效 | `SFX_` + 名字 | `SFX_Jump.wav` |
| 音乐 | `BGM_` + 名字 | `BGM_Level01.ogg` |

**三条硬规则**：

1. **不用空格**，用下划线（空格在命令行 / CI 里是雷）
2. **不用中文文件名**（同上）
3. **不用 `New` / `Copy` / `Final` / `Final2`**——这是 4 人团队冲突的最大来源

## 五、四人分工

### 5.1 分工原则

1. **按架构层切，不按「一人一个功能」切**——同一层的模块互相依赖，拆给两个人会天天对齐接口
2. **每人独占一个程序集**——互不干扰，编译不冲突
3. **底座先行**——Infrastructure 和 Core 是所有人的依赖，必须先冻结接口
4. **属性规则类是可分配的最细粒度**——基类冻结后，7 个属性规则类是 7 个独立任务

### 5.2 分工表

| | 负责 | 交付物 | 程序集 |
|---|---|---|---|
| **P1** | 基础设施 + 存档 | 时间管理器、快照系统、关卡流程、对象注册表、存档读写 | `Infrastructure` · `Persistence` |
| **P2** | 规则系统 | 规则维护表、属性管理器、属性规则类基类、**7 个属性规则类** | `Core` |
| **P3** | 玩家 + 战斗 | 玩家移动控制、玩家状态（含能量）、规则释放入口、伤害结算、命中判定 | `Gameplay` |
| **P4** | 敌人 + 场景叙事 + UI | 敌人 AI、敌人状态、场景触发器、NPC 台词、HUD、拼装界面 | `Gameplay` · `UI` |

> ⚠️ **P3 和 P4 共用 `Gameplay` 程序集**。这是有意的——玩家和敌人必须走**同一套属性查询**（架构约束），
> 分成两个程序集会诱导人写出「玩家特例」。代价是两人要频繁同步，用分支 + 每日合并来管理。

### 5.3 关键路径与并行

```
        ┌─ P1 基础设施 ─┐
        │               │
第 1 天 ─┤               ├─→ P2 规则系统 ─→ P3/P4 玩法
        │               │
        └─ 接口冻结 ────┘
```

**P1 和 P2 在关键路径上，他们卡住所有人。** 所以：

| 阶段 | P1 | P2 | P3 | P4 |
|---|---|---|---|---|
| **第 1-2 天** | 时间管理器 + 快照系统骨架 | 规则维护表 + 属性管理器 | 玩家移动控制（先不接规则） | 关卡白盒 + HUD 骨架 |
| **第 3-7 天** | 快照系统完整 + 关卡流程 | 属性规则类基类 + 重力/摩擦/质量 | 规则释放入口 + 战斗 | 敌人 AI + 拼装界面 |
| **第 8-14 天** | 存档 + 对象注册表 | 剩余 4 个属性规则类 | 玩家完整 + 数值调优 | 场景叙事 + NPC 台词 |
| **第 15-21 天** | 稳定性 / Bug | 规则数值平衡 | 手感打磨 | UI 打磨 + 结算 |

### 5.4 属性规则类的分配（P2 的活可以再分）

基类 `AttributeRuleBase` 冻结后，**7 个属性规则类是 7 个互不干扰的任务**，可以分给全队：

| 属性 | 难度 | 建议给谁 |
|---|---|---|
| 重力 | 低 | P2 |
| 摩擦 | 低 | P2 |
| 质量 | 低 | P2 |
| 伤害 / 生命 | 中 | P3（和战斗同一个人） |
| 关系 | 中 | P4（和敌人阵营同一个人） |
| 时间 | **高** | P1（和快照系统同一个人） |
| 因果 | **高** | 暂缓，见 [规则矩阵.json](规则矩阵.json) 的 undecided |

> **时间规则给 P1** 是有意的：时间恒定和时间反转都要用快照系统，同一个人写能保证两者共用一套基础设施。

### 5.5 每人第一天该做的第一件事

| | 第一件事 |
|---|---|
| **P1** | 按 [接口与事件定义.md](接口与事件定义.md) 3.1 / 3.2 实现 `ITimeManager` 和 `ISnapshotSystem` 的空壳 |
| **P2** | 按 2.1 / 2.2 实现 `IRuleTable` 和 `IAttributeManager` 的空壳 |
| **P3** | 按 4.3 实现 `IRuleRelease` 的空壳，用假的 RuleSystem 跑通玩家移动 |
| **P4** | 搭 `Level_01` 白盒，实现 `IEntityStatus` 让能量/生命能显示在 HUD 上 |

**「空壳」指：接口方法全部实现，但内部是 `Debug.Log` 或返回默认值。**
这样 4 个人第一天就能各自跑起来，不用等别人。
